# 下推（单据转换）与反写插件指南

> 示例链路：**采购订单 `PUR_PurchaseOrder` →（下推）→ 采购入库单 `STK_InStock` →（审核反写）→ 采购订单已入库数量**
> 对应代码：`KingdeeSky.Plugins.Convert.PurchaseOrderToInStockConvertPlugin`（转换插件）、
> `KingdeeSky.Plugins.Convert.PurchaseInStockWriteBackPlugin`（反写插件）。

---

## 1. 一张图理解 BOTP（单据转换与反写）

```
 采购订单(上游/源单)                 采购入库单(下游/目标单)
┌──────────────────┐  ①转换规则/下推   ┌──────────────────┐
│ 数量 FQty=100    │ ───────────────▶ │ 实收数量 FRealQty│
│ 已入库数量       │  字段映射/选单条件 │ 关联表(LK)记录来源 │
│ (反写目标字段)   │                   └────────┬─────────┘
│                  │  ②反写规则(保存/审核触发)   │ 保存/审核：按关联表
│ ◀─────────────── │ ◀───────────────────────┘ 计算反写量，回写源单
└──────────────────┘   反审核/删除：回滚反写
```

- **转换规则（BOTP 规则）**：定义源单→目标单的字段映射、分录匹配、选单条件、转换策略；
  下推时平台按规则生成目标单数据包，**转换插件**负责规则表达不了的补充逻辑。
- **反写规则**：下游单据保存/审核时，按关联关系把数量/金额回写到上游单据（如已入库数量、未清数量）；
  **反写插件**干预反写过程。反审核、删除下游单时平台自动回滚反写。
- **网控（超额控制）**：限制下游数量超过上游的比例/数值，超额时提示或阻断。

## 2. 配置转换规则（采购订单 → 采购入库单）

1. BOS 设计器中打开 **业务流程设计 / 单据转换规则**（不同版本入口名为“转换规则”“业务流程-单据转换”）。
2. 新建转换规则：源单表单 = 采购订单 `PUR_PurchaseOrder`，目标单表单 = 采购入库单 `STK_InStock`，
   选择目标单据类型。
3. 配置**字段映射**：表头（供应商、采购组织、库存组织等）、分录（物料、数量、仓库、需求日期等）；
   关联字段（Link）保持默认，平台据此建立上下游关联。
4. 配置**转换策略/选单条件**（如只下推未关闭、未完全入库的分录）。
5. **注册转换插件**：在规则的“插件/插件策略”页签新增，注册
   `KingdeeSky.Plugins.Convert.PurchaseOrderToInStockConvertPlugin, KingdeeSky.Plugins`，
   保存后将规则**停用再启用**一次，确保插件挂载。
6. 保存并启用规则，做业务对象功能授权。
7. 验证：采购订单界面点【下推】→ 选“采购入库单”→ 生成目标单；
   断点打在 `AfterConvert`，附加 w3wp 后命中。

> 标准产品通常已预置“采购订单→采购入库单”规则，优先**扩展预置规则**而不是新建，
> 避免破坏标准流程（MRP、库存、应付的上下游追踪都依赖它）。

## 3. 转换插件事件链（C#）

基类：`Kingdee.BOS.Core.Metadata.ConvertElement.PlugIn.AbstractConvertPlugIn`
参数：`Kingdee.BOS.Core.Metadata.ConvertElement.PlugIn.Args.*`
结果数据包：`ExtendedDataEntity`（命名空间 `Kingdee.BOS.Core.Metadata.ConvertElement`）

| 方法 | 时机 | 典型用途 |
|---|---|---|
| `OnQueryBuilderParemeter` | 查询源单数据前（官方拼写 Paremeter） | 追加需要加载的源单字段 |
| `OnFieldMapping` | 字段映射前 | 调整映射上下文 |
| `AfterFieldMapping` | 单字段映射后 | 按源单值修正目标字段、按子单据体拆行 |
| `OnCreateTargetBill` / `AfterCreateTargetBill` | 目标单数据包创建前后 | 改单据类型、合并/拆分目标单 |
| `AfterConvert` | **全部转换完成后（最常用）** | 遍历 `e.Result.FindByEntityKey("FBillHead")` 补字段 |

示例要点（见源码）：

```csharp
ExtendedDataEntity[] heads = e.Result.FindByEntityKey("FBillHead");
Field noteField = e.TargetBusinessInfo.GetField("FNote");
Entity entry = e.TargetBusinessInfo.GetEntity("FInStockEntry");
foreach (var head in heads)
{
    var rows = head[entry.DynamicProperty] as DynamicObjectCollection; // 目标单分录
    head[noteField.DynamicProperty] = "转换插件补充的备注";             // 改表头
}
```

> 经验：下推过程**不触发界面的值更新事件**，“带基础资料属性到指定列”等界面规则不会执行，
> 这类字段都在 `AfterFieldMapping`/`AfterConvert` 里补。调试时先在 AfterConvert 断点，
> 逐层展开 `e.Result` 数据包（把它当 JSON 看），确认字段路径后再写赋值。

## 4. 配置反写规则

1. 主控台搜索 **【反写规则】** 并打开，点新增（反写规则类似基础资料，全局唯一）。
2. 填写上游单据（采购订单）、下游单据（采购入库单），绑定对应的转换规则。
3. 配置反写条目：
   - **下游取值字段（公式）**：如入库单实收数量 `FRealQty`；
   - **上游反写字段**：采购订单已入库数量字段（标准字段，通常为分录关联数量字段）；
   - **反写方式**：累加（数量类常用）/覆盖（文本类常用）；
   - **反写触发操作**：保存、审核（按需勾选）；
4. **超额控制（网控）**：设置是否允许超出上游数量、超量比例与提示文案；为空用系统默认提示。
5. 保存后回到转换规则/业务流程中确认反写规则已挂载；标准链路一般已预置，扩展即可。
6. **复制规则 GUID**：打开反写规则记录，复制其内码/唯一标识，替换
   `PurchaseInStockWriteBackPlugin.TargetRuleId`（或首次调试时在 `BeforeWriteBack` 断点查看 `e.Rule.Id`）。
7. **注册反写插件**：BOS 设计器扩展下游单据（采购入库单），在表单的
   **业务流程服务插件/反写插件**节点注册
   `KingdeeSky.Plugins.Convert.PurchaseInStockWriteBackPlugin, KingdeeSky.Plugins`。
   注意：反写插件是**单据级公用**的，会拦截该单全部反写规则，代码中必须按 `e.Rule.Id` 过滤。

## 5. 反写插件事件链（C#）

基类：`Kingdee.BOS.Core.BusinessFlow.PlugIn.AbstractBusinessFlowServicePlugIn`
参数：`Kingdee.BOS.Core.BusinessFlow.PlugIn.Args.*`
（⚠️ 网上 `AbstractWriteBackPlugIn` + 驼峰方法名是**苍穹 Java 版**，星空 C# 不可用。）

| 方法 | 时机 | 典型用途 |
|---|---|---|
| `BeforeTrackBusinessFlow` | 业务流程跟踪、反写分析前 | 取消整单反写 |
| `BeforeCreateArticulationRow` | 构建每行关联数据前 | 取消本行反写/分配 |
| `BeforeReadSourceBill` | 读取上游单据前 | 追加要加载的源单字段 |
| `BeforeWriteBack` | 每条反写规则执行前 | 按 `e.Rule.Id` 过滤、缓存上下游字段元数据 |
| `AfterCalcWriteValue` | 反写量计算完毕 | **修正反写量、调整对各源单行的分配** |
| `BeforeExcessCheck` / `AfterExcessCheck` | 超额检查前后 | 自定义超额判定 |
| `AfterCommitAmount` | 反写量写入源单行之后 | 反写后扩展动作（本示例在此写审计日志） |
| `BeforeSaveWriteBackData` | 反写数据落库前 | 保存/删除时的自定义回退逻辑 |

触发与回滚：下游**保存/审核**时按关联信息逐规则反写；**反审核/删除**时按历史反写记录自动回滚
（`this.OperationNumber` 区分 Save/Audit/Delete/UnAudit）。

## 6. 平台限制（来自官方社区经验，先知道边界）

1. 平台反写规则只支持**关联实体及其父实体**（最低到单据体）；反写**子单据体**必须用插件处理。
2. 不支持配置**两层反写**（B 反写 A 后再反写 A 的上游），需要插件/二开串联。
3. 覆盖模式反写相对简单；累加/累减模式若插件介入，需自行处理历史反写值，复杂度高。
4. 一张下游单挂多条反写规则时，注意执行顺序与字段互相覆盖，插件务必按规则 GUID 隔离。

## 7. 用 WebAPI 下推

下推端点：`Kingdee.BOS.WebApi.ServicesStub.DynamicFormService.Push.common.kdsvc`
（部分版本为 `Convert`；以主控台【公共设置→动态服务定义→WebAPI】在线测试页为准。）请求体示例：

```json
{
  "formid": "PUR_PurchaseOrder",
  "data": "{\"Ids\":\"采购订单内码\",\"RuleId\":\"转换规则Id(空则用默认规则)\",\"TargetFormId\":\"STK_InStock\",\"TargetBillTypeId\":\"\",\"IsEnableDefaultRule\":\"true\",\"CustomParams\":{}}"
}
```

Push 成功后目标单通常为“已暂存/已保存”状态，再按返回内码调用 Submit、Audit；
审核成功即触发反写。建议先在 WebAPI 在线测试页选“采购订单→Push”跑通，再把 JSON 搬进代码。

## 8. 调试要点

- 转换插件：下推动作发生在源单界面/服务端，附加 `w3wp.exe`，在 `AfterConvert` 断点；
- 反写插件：在下游单**保存或审核**时触发，断点打 `BeforeWriteBack`、`AfterCommitAmount`；
- 看不到断点：确认规则停用再启用过、插件注册在正确的规则/下游单据上、DLL 已更新（[HotUpdate]
  热更新对 1 小时内替换的 DLL 生效，否则回收应用程序池）；
- 反写结果核对：源单分录的关联数量列，或关联关系表（LK 表）与反写历史，按账套实际表结构核对。
